# Application continuation instructions

Use these instructions alongside `SKILL.md` and the application workspace's current `AGENTS.md`. Read the latest user messages and saved, scoped authorization before resuming. Personal configuration belongs in the private workspace, outside the reusable skill.

## Email and account routing

Use the user's latest explicit application email for remaining forms. A later correction supersedes an earlier batch exception. Record the email actually used with each application; preserve the historical email on already-submitted applications.

Before entering application data, verify the employer tenant and signed-in account. If a pending form locks a different account email, hold only that role and continue other authorized applications. Do not silently use the old address, create a duplicate profile, or change an authentication identifier to work around the mismatch. Explain the concrete account limitation once.

Before asking for login help, check the existing authorized session and available browser/password-manager saved credential, including the user's saved common credential when approved for that destination. Never guess, reconstruct, print, commit, or save passwords or authentication tokens. Credential changes follow the active tool's handoff rules.

## Required facts and surveys

Reuse verified answers only when the country, employer, time and wording match. General work authorization does not establish a particular permit type, expiration date, unrestricted work rights, citizenship or clearance.

Keep technical proficiency, experience setting and personal interest separate. A high interest rating does not mean expert proficiency; classroom use does not establish professional experience. Batch required missing questions, persist the user's exact answers with scope and provenance, and continue independent authorized roles while awaiting replies.

Use the approved resume for the selected internship or graduate track. Verify the actual employer attachment and indexed source hash. Check the native education and graduation fields against current verified facts; a historical or future degree date must not become a completed degree claim. If a form cannot represent a required fact accurately, preserve the draft and record the limitation.

## Submission and recovery

Apply existing destination/data consent without repeating routine approvals. New exceptional actions still follow the active tool's confirmation rules. Respect a user's decision not to help with a blocked portal and continue other authorized work.

Record `submission_unknown` and a submission-attempt event before one final Submit click. If the page transitions or a DOM read times out, inspect the employer result using another supported observation, such as its visible screenshot or accessibility view. Verify the same requisition. Do not treat an observation timeout as a reason to click Submit again.

Only employer receipt text or verified account history establishes `applied`; Jobright badges alone do not. A processing error remains unconfirmed until reconciled. Save evidence, the exact blocker and the next action; preserve a resumable checkpoint. A blank embedded panel means the portal is inaccessible, not that the job is closed. Never bypass verification or security controls.

Use saved recovery delays and submission intervals across the entire batch. Update exact application IDs and requisitions, preserve unrelated records and workbook sheets, and refresh the Excel tracker before reporting outcomes. Report confirmed submissions separately from drafts, blockers and uncertain attempts.

## Publishing and synchronization

Verify repository visibility from GitHub before publishing personal configuration or a workspace archive. A local README calling a repository private is not proof of its current visibility. A request to update instructions authorizes instruction changes; it does not implicitly authorize uploading a new profile, resume, tracker, credential or evidence archive.

Publish reusable workflow guidance without personal identifiers. Personal synchronization requires a verified private destination and the applicable explicit data authorization. Preserve existing history; changing visibility cannot recall copies previously downloaded. Never change repository visibility or rewrite history as an unrequested side effect of an instruction update.
